Debugging Workflow
How to work a bug down to root cause

Don't ask 'fix this'. Ask Claude to investigate before proposing fixes. Provide the failing case, the actual vs expected, and the relevant code. Let Claude propose hypotheses, then verify each.

  • Show the failing input, the actual output, and the expected output
  • Paste only the code that's likely involved (Claude isn't your editor)
  • Ask: 'What are 3 possible causes? For each, what's the diagnostic that confirms or rules it out?'
  • Have Claude pick the most likely, propose the fix, then verify against another test case
1
Capture the failing case precisely
Input, actual output, expected output. Be exact about what 'failing' means.
2
Paste only the relevant code
Don't paste the whole file. Paste the function involved and any direct callers.
3
Ask for hypotheses, not fixes
'What are 3 possible causes? For each, what's the diagnostic to confirm or rule out?'
4
Run the diagnostics
Test each hypothesis against the actual code. Most hypotheses fail; one survives.
5
Ask for the fix based on the surviving hypothesis
Now you have root cause; the fix is straightforward.

✅ DO THIS

  • Show the failing input, actual output, and expected output explicitly
  • Paste only the code that's likely involved (the function plus direct callers)
  • Ask for hypotheses ranked by likelihood, with diagnostic for each
  • Test each diagnostic before accepting any fix
  • Have Claude explain the fix after applying it — confirms understanding

❌ AVOID THIS

  • Pasting the whole file — Claude isn't your editor
  • Asking 'fix this' without showing what 'failing' means
  • Accepting the first proposed fix without diagnostic verification
  • Iterating fixes without understanding root cause — symptom-chasing
  • Forgetting to share constraints (language version, framework, deployment target)

The debugging pattern that works isn't 'paste the bug, ask Claude to fix it'. It's structured: show the input, the actual output, the expected output, and the code involved. Then ask Claude to propose hypotheses rather than fixes. Hypotheses are testable; fixes are gambles.

Once Claude has proposed 3-4 hypotheses ranked by likelihood, ask for the diagnostic that would confirm or rule out each. Run the diagnostics. Pick the surviving hypothesis. Then ask for the fix. This pattern reliably finds root causes; the 'fix it and see' pattern reliably finds symptoms.

Code Review Pattern
Using Claude as a second pair of eyes

Code review is one of the highest-leverage uses. Claude is excellent at spotting subtle correctness issues, missing edge cases, and style inconsistencies — often catching things humans miss in busy reviews.

  • 'Review this PR. Focus on correctness, edge cases, and anything that could fail in production.'
  • 'What edge cases am I not handling here?'
  • 'Is there a simpler way to express this?'
  • 'Would this work correctly with concurrent access?'

Claude as a code reviewer is genuinely useful — it catches edge cases humans miss in busy reviews, spots stylistic inconsistencies, and never gets defensive about its own previous work. The trade-off is that it can be over-cautious; you'll often need to dismiss 30-40% of its suggestions as not worth doing.

The strongest prompt is targeted: 'Review this PR for correctness and edge cases. Skip style nits.' or 'What edge cases am I not handling here?' Generic 'review this' prompts produce generic 'here are 17 things' responses.

The targeted-review prompts that work

Generic 'review this' produces generic 'here are 17 things'. Specific review prompts produce specific findings worth acting on.

  • 'Review this PR for correctness and edge cases. Skip style nits.'
  • 'What edge cases am I not handling? Test inputs that would surface them.'
  • 'Is there a simpler way to express this? Show me the simplest equivalent.'
  • 'Would this work correctly with concurrent access? What are the race conditions?'
  • 'What would break if this scaled 1000x? What's the bottleneck?'
  • 'Security review — what are the top 3 attack vectors against this code?'

Refactoring Pattern
Mechanical changes at scale

For refactors that span many files, use Claude Code. For smaller refactors, Chat or Cowork works well.

  • Describe the before-state and desired after-state
  • Ask Claude to propose the plan before writing code
  • Review the plan, adjust, then execute
  • Test after each substantial step, not at the end
1
Describe before-state and after-state clearly
'Current: X. Target: Y. The behaviour should remain identical; only the structure changes.'
2
Ask for the plan before the code
'Walk through the refactor as a plan first. List the files and the order of changes.'
3
Validate the plan against your knowledge
'Show me which sequence is safest. Where could intermediate states break tests?'
4
Execute step by step, testing after each
Don't apply the whole plan at once. Apply one step, run tests, then continue.
5
Have Claude summarise what changed
Final summary serves as the PR description and the doc for future reviewers.

Honest Limits
Where Claude can still go wrong
⚠️ ALWAYS TEST, ALWAYS READ
Claude writes plausible code. Plausible isn't the same as correct. Run the code. Read what Claude wrote. The fastest way to ship a subtle bug is to commit AI-written code without reading it.
  • Specific API versions — always verify against docs for the version you're on
  • Library internals — Claude knows surface, not always implementation details
  • Performance reasoning — Claude can't profile your actual code
  • Security — Claude can spot common issues but isn't a substitute for security review
⚠️ WHERE CLAUDE STILL GETS IT WRONG
Specific API versions (always verify against current docs), library internals (knows surface, sometimes wrong on implementation), performance reasoning (can't profile your actual code), and security review (catches common patterns but isn't a substitute for proper review).

Common Mistakes & Fixes
What goes wrong — and how to avoid it

Most AI workflows that 'don't work' fall into one of these patterns. The fix is almost always sharper context and stricter review, not switching models or tools.

  • Treating Claude for Coding Assistance as a finished answer rather than a draft to review
  • Vague prompts that don't specify audience, format, or what you want changed
  • Forgetting to give it context — the file, the brief, the constraints
  • Skipping the verify step — always check numbers, dates, names, and policy claims
  • Using it for tasks where a 30-second human action would be faster

✅ DO THIS

  • Provide context — the file, the brief, the audience, the constraints
  • Iterate; don't just accept the first output
  • Always review numbers, names, dates, and policy claims
  • Treat AI as a fast draft generator, not an answer engine
  • Capture what works so you can replicate it
  • Match the model to the task — fast modes for drafts, reasoning modes for analysis

❌ AVOID THIS

  • Sending AI output without reading it end-to-end
  • Vague prompts with no audience, format, or success criteria
  • Assuming AI can see files or context it hasn't been given
  • Using AI for tasks faster done manually in under a minute
  • Treating numbers, quotes, or citations as verified without checking
  • Defaulting to the slow reasoning mode for every task
